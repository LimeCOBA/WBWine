# Как работает Atlas

## Что проверяла первая версия

В ledger/test_workflow.py ноды A и B создавались внутри временной БД, а время, цена и вместимость рейса задавались тестом. Это позволяло проверить сохранение заказа, выдачу и запрет переполнения. Прежний Atlas перебирал цепочки опубликованных рейсов. Географических координат, дорожной сети, балансировки партии и обученной модели в нём не было. В прежнем README ограничения перебора перечислялись в разделе «Расчёт», отсутствие географии и двух решателей явно не обозначалось.

## Дорожная сеть

domain/roads.py хранит приближённые координаты шести городов и список двусторонних дорог с заданной длиной в километрах. Координаты задают положение города на схеме, километры принадлежат дорожным рёбрам. Это версия виртуальной сети для моделирования. Километраж и трассировки конкретных поездок в реальной России требуют отдельного источника. Дейкстра восстанавливает кратчайший дорожный путь между парой городов. Внутри одного города межгородской пробег равен нулю. Адресная последняя миля пока не моделируется. Нода привязана к городу. Для старых записей город можно указать в администрировании.

## Планирование партии

В кабинете Atlas откройте «Распределить партию». Введите запас одинаковых грузовых единиц у отправителей и потребность у получателей. Пустые поля означают ноль. Общие объёмы должны совпадать. Обе модели получают одинаковую матрицу кратчайших дорожных расстояний d. Для x единиц между i и j задача минимизирует S = Σ dᵢⱼ xᵢⱼ при x ≥ 0, заданных суммах по строкам и столбцам. Размерность S — единица груза × км. При единой положительной ставке r и постоянной добавке F выполняется C = rS + F, поэтому минимумы совпадают. При разной цене рейсов, времени хранения или тарифах эта эквивалентность может нарушиться.

* Симплекс. scipy.optimize.linprog решает задачу двойственным симплексом HiGHS. При целочисленных запасах и спросе базисный транспортный план целочислен. После округления численного результата проверяются балансы.
* ИИ. Дерево регрессии при первом использовании обучается локально на 180 синтетических задачах, размеченных симплексом. Оно предсказывает приоритет пары по расстоянию, отклонению от минимальных расстояний и долям запаса и спроса. Распределитель обходит пары по прогнозу и переносит минимум оставшихся объёмов. Получается допустимый план без гарантии минимума. Обучение воспроизводимо, результат обучения кешируется в процессе. Реальных исторических перевозок для обучения пока нет.

Пример для ручной проверки: Москва отдаёт 2 единицы, Чебоксары — 3. Владимир запрашивает 3, Казань — 2. Оптимум равен 1165 ед·км: две единицы проходят по 190 км, одна — 475 км, ещё две — по 155 км. В кабинете можно повторить расчёт другим методом с тем же вводом.

## Граница с операционным контуром

План партии показывает, сколько одинаковых единиц перевезти между городами. Он не создаёт рейсы, не назначает конкретные посылки и не резервирует машины. Вместимость отдельных дорог, число машин, порожние пробеги и пробки в этой задаче не учитываются. Автоматическое превращение плана партии в расписание не реализовано.

Для отдельной посылки Seller и Atlas проверяют опубликованные Fleet рейсы, забронированные литры, массу, пересадки и срок. В снимок новой оценки входят дорожные города и километры каждого плеча. Публикует время и транспортную цену перевозчик. Wild использует эту цену и стоимость хранения для выбора допустимой цепочки по рублям. Для адресов без города интерфейс сообщает об отсутствии данных плеча.

## Проверка

Запуск из корня: `.venv\Scripts\python.exe manage.py test ledger`. В ledger/test_transport.py проверяются дорожная цепочка, аналитически известный оптимум, балансы ИИ, неверный ввод и вызов обоих методов через защищённый API Atlas. Такие тесты устанавливают корректность на контрольных примерах. Точность дорожных данных и качество модели на реальном потоке заказов не измерялись.
